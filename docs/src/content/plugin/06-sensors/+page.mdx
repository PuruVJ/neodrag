A **sensor** is the layer that turns raw device input — a pointer down, an arrow key, a stick deflection — into the normalized interaction stream the engine routes to whichever capability owns a node. Sensors sit one level below `Draggable`/`Droppable`/`Resizable`/`SortableList`: a capability decides _what_ a gesture means, a sensor decides _what counts as_ a gesture.

You almost never touch this page. The framework wrappers and the shared engine wire up the default sensors for you, so a plain `Draggable` already responds to pointer and keyboard out of the box. Sensors are the seam you reach for when you want a non-default input source (a gamepad), or a non-default engine (no auto-install, a custom delegate root).

## The default sensors

Every engine installs three sensors the first time a capability is added to it — and since the single-element classes all share one process-wide engine, that happens automatically:

- **`PointerSensor`** — mouse / touch / pen via Pointer Events. Left button only by default.
- **`KeyboardSensor`** — cancels the active interaction on <kbd>Escape</kbd>.
- **`KeyboardMoveSensor`** — grab-and-move with the keyboard (see below).

You don't import or register any of these for the common case. This page documents what they are so the rest makes sense.

## Keyboard dragging

The `KeyboardMoveSensor` is installed by default, but it only acts on nodes that have been **registered** as keyboard-movable. Registration is a separate, engine-level call — `keyboardDraggable(node, options)` from `@neodrag/core/sensors` — because it's independent of the drag capability (the same registry also drives the gamepad).

Once a focusable node is registered, the user presses the grab key (<kbd>Space</kbd> by default) to grab it, moves it with the arrow keys, and presses the grab key again to drop. <kbd>Escape</kbd> cancels. Holding an arrow auto-repeats, speeding up after a moment.

```js
import { keyboardDraggable } from '@neodrag/core/sensors';

// node must be focusable so it can receive the grab keystroke
const node = document.querySelector('.box');
node.tabIndex = 0;

const handle = keyboardDraggable(node, {
  grabKey: 'Space', // key (or 'Space') that grabs / releases. Default 'Space'
  step: 1, // px per arrow press (slow phase). Default 1
  fastStep: 4, // px per tick once auto-repeat speeds up. Default 4
  axis: null, // 'x' | 'y' | null (free). Default null
  slowInterval: 400, // ms between repeats before speed-up. Default 400
  speedupDelay: 800, // ms held before repeats speed up. Default 800
  fastInterval: 50, // ms between repeats after speed-up. Default 50
});

handle.update({ step: 2 }); // re-register with new config
handle.destroy(); // unregister
```

The resulting move inputs flow through the same engine, so whichever capability owns that node (e.g. `Drag`) handles them exactly like a pointer drag — the position updates, callbacks fire, bounds and grid still apply.

Pair this with the `ariaDrag` extension (see [Extras](/docs/extras)) for live screen-reader announcements on grab / move / drop. `ariaDrag` is a `use:` extension on the capability, not a sensor — it gates its announcements to keyboard input.

## Gamepad

The `GamepadSensor` is **not** installed by default — import it and register it on an engine. It polls connected gamepads each frame and maps the left stick + d-pad to move inputs, **A** to grab/commit and **B** to cancel. It drives the same keyboard-drag registry, so a gamepad moves any node you've passed to `keyboardDraggable` — whichever one currently holds focus.

For the single-element classes, register it on the shared engine via `sharedEngine()`:

```js
import { sharedEngine } from '@neodrag/core';
import { GamepadSensor } from '@neodrag/core/sensors';

sharedEngine().registerSensor(
  new GamepadSensor({
    deadzone: 0.25, // stick magnitude below this is centered. Default 0.25
    speed: 12, // steps/second at full deflection. Default 12
  }),
);
```

`registerSensor` is idempotent per sensor key — registering the same sensor twice is a no-op — and a sensor added after the engine is already running is set up immediately.

## A standalone engine

When you want full control — no auto-installed sensors, a custom delegate element, or a sandbox separate from the shared engine — construct a `Interactions` yourself with `defaultSensors: false` and register exactly the sensors you want. This is the framework-author / advanced path; see [Core](/docs/core) for the engine surface.

```js
import { Interactions } from '@neodrag/core';
import { PointerSensor, KeyboardSensor, GamepadSensor } from '@neodrag/core/sensors';

const engine = new Interactions({
  defaultSensors: false, // skip the auto pointer + keyboard install
  delegate: () => document.documentElement, // root the single listeners here
});

engine
  .registerSensor(new PointerSensor())
  .registerSensor(new KeyboardSensor())
  .registerSensor(new GamepadSensor());

// engine.use(drag, drop, …) to compose capabilities — see Core
// engine.dispose() to tear down sensors + the active session
```

With `defaultSensors: false` the engine installs nothing on its own, so an engine you never register a sensor on receives no input at all.

## Customizing the pointer sensor

`PointerSensor` claims the left button only. Pass a `buttons` allow-list (mouse button indices: `0` left, `1` middle, `2` right) to start interactions from other buttons:

```js
import { PointerSensor } from '@neodrag/core/sensors';

// allow middle-click drags too
new PointerSensor({ buttons: [0, 1] });
```

> The engine ignores the right button (`2`) for starting interactions regardless, reserving it for context menus.

`KeyboardSensor` takes a `cancelKeys` list (default `['Escape']`) if you want additional keys to abort the active interaction:

```js
import { KeyboardSensor } from '@neodrag/core/sensors';

new KeyboardSensor({ cancelKeys: ['Escape', 'Backspace'] });
```

## Input filters

For sensors that accept them, `@neodrag/core/sensors` exports small composable predicates over a normalized input — the seam for deciding whether an input should drive an interaction. Pointer-only checks pass non-pointer (keyboard / programmatic) inputs straight through.

```js
import { allFilters, buttonFilter, modifierFilter } from '@neodrag/core/sensors';

// left-button drags, only while Shift is held
const filter = allFilters(buttonFilter([0]), modifierFilter({ shift: true }));
```

- `buttonFilter(buttons)` — pass pointer inputs whose button is in the list.
- `modifierFilter({ shift?, ctrl?, alt?, meta? })` — pass when every named modifier matches; an explicit `false` requires that modifier be released; omitted keys are unconstrained.
- `allFilters(...filters)` — AND-composition; passes only when every filter passes.

## Writing a sensor

A sensor is just an object with a unique `key` and a `setup(host)` that wires up listeners and returns a teardown. Extend `SensorBase` and implement `attach` — it's handed a `SensorHost` you call to drive the engine:

```js
import { SensorBase } from '@neodrag/core/sensors';
import { pointerToInput } from '@neodrag/core/interaction';

const MY_SENSOR_KEY = Symbol('neodrag.sensor.my');

class MySensor extends SensorBase {
  key = MY_SENSOR_KEY;

  attach(host) {
    const target = host.getDelegate();
    const onDown = (e) => {
      host.onInteractionStart(pointerToInput(e, 'start'));
      // …drive host.onInteractionMove / onInteractionEnd from your own events
    };
    target.addEventListener('pointerdown', onDown, { capture: true });
    return () => target.removeEventListener('pointerdown', onDown, { capture: true });
  }
}
```

The `SensorHost` surface: `getDelegate()` (the element the single listeners live on), `onInteractionStart/Move/End(input)`, `cancelActive(reason)`, and `setPointerDisarm(fn)`. Build inputs with the helpers from `@neodrag/core/interaction` (`pointerToInput`, `keyboardToInput`) so they're normalized the way the engine expects. Register your sensor with `engine.registerSensor(new MySensor())`.
